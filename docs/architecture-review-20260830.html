3. Dead & Vestigial Abstractions

IngestorService (normalizer.py:226-243)

A "high-level service interface" that does nothing except re-import and call seed_database and seed_competition from seeder.py. Zero callers in production. Zero test coverage. Creates the circular normalizer → seeder import.

Action: Delete entirely. This is the source of the normalizer → seeder circular import.

get_format_adapter() factory + aliases (format_adapters.py:642-652)

get_format_adapter(format_engine, name) always returns CompetitionSyncAdapter() regardless of inputs. LeagueFormatAdapter and GroupKnockoutAdapter are aliases for the same class. fetch_games_with_fallback is a lambda that returns ([], False). These exist "for backward compatibility" but their only callers are in updater.py which could call CompetitionSyncAdapter() directly.

Action: Replace 4 callers in updater.py with CompetitionSyncAdapter() directly. Delete aliases and dead factory.

CacheAdapter (normalizer.py:120-162)

Generates date-prefixed cache paths and wraps fetch_json_with_retry — but utils.py already has identical _get_cache_path() logic (lines 12-27). The CacheAdapter is only used by IngestorService which is dead. Two implementations of the same caching scheme exist in the codebase.

Action: Delete with IngestorService. Keep utils.py as the canonical cache path generator.

Production mock detection (format_adapters.py:403-405)

is_mocked = hasattr(updater_module.fetch_json, "return_value") or type(…).__name__ in ("MagicMock", "Mock"). Production code that inspects whether it's running under a test mock. This is a test concern leaking into production — the entire "is_mocked" code path (lines 405-469) is a 65-line test hook embedded in production code.

Action: Extract into a test-specific adapter. Production code should never inspect mock state.

Fixture.latest_odds FallbackOdds inner class (database.py:190-194)

A dynamically-defined inner class created every time latest_odds is called on a fixture with no odds. Returns hardcoded (2.0, 3.0, 2.0). This is a model concern that should be a default at the odds layer, not an anonymous class inside a property.

init_db() ALTER TABLE shim (database.py:282-289)

Runs ALTER TABLE teams ADD COLUMN logo_url VARCHAR in a try/except on every SQLite init. This was a migration workaround. Since logo_url is now in the Team model and Alembic manages migrations, this is dead code.

Candidate 1: Collapse the Seeder pipeline

Strong seeder.py — 958 lines, 12 commits, #1 hotspot

Problem: seeder.py is simultaneously: (a) a WC group/player data file (~300 lines of hardcoded dicts), (b) the call_football_api() HTTP helper imported by 2 other modules, (c) team upsert logic that duplicates TeamResolver, (d) fixture upsert logic that duplicates FixtureUpserter, (e) odds/standings orchestration, and (f) European cup seeding from JSON files. Every responsibility is exposed as a top-level function — callers must know the correct function and call sequence.

Evidence:

  • 8 top-level functions exported (seed_database, seed_all_default_competitions, seed_single_competition, fetch_and_seed_teams, seed_competition, seed_european_cups, call_football_api, get_fallback_matches)
  • 5 call-sites: main.py, cli.py, api_admin.py (×2), normalizer.py (circular)
  • ~300 lines are static data (ELO_RATINGS, GROUPS, SPOTLIGHT_PLAYERS) that belong in JSON files
  • team_resolver.py already handles team resolution but seeder.py has its own inline version (line 618-690)
  • fixture_upserter.py already handles fixture upsert but seeder.py has its own (lines 300-390)

Solution: Extract static data to JSON. Make seeder.py a thin orchestrator that delegates to IngestionEngine (already exists), TeamResolver, and FixtureUpserter. Move call_football_api to providers/api_football.py (where a copy already exists). Single interface: seed(db, config) → SeedResult.

Candidate 2: Extract a Fixture Lifecycle module

Critical settle_result + update_fixture_score — 10 paired call sites

Problem: Finishing a fixture requires calling settle_result() (from settling.py) then update_fixture_score() (from scoring.py) as a pair. This is scattered across 10 call sites in 4 files. If any site forgets update_fixture_score(), the fixture is settled but its watchability data is stale. This has happened — seeder.py:329 calls settle_result() without update_fixture_score().

Evidence:

  • updater.py: 4 paired calls (lines 117+134, 132+134, 182+199, 197+199)
  • format_adapters.py: 4 paired calls (lines 456+457, 508+509, 577+578, 625+626)
  • elo.py: 1 paired call (line 279)
  • seeder.py:329: calls settle_result() without update_fixture_score() — live bug
  • seeder.py:391: calls update_fixture_score() but 62 lines after the settle — fragile ordering

Additionally: Team streak updates are implemented twice: settling.py:update_team_streaks() updates streaks on settle, but standings.py:recalculate_team_streaks() re-does the entire calculation from scratch. Both mutate the same Team fields. If both run, the standings.py version silently overwrites settling.py's incremental updates.

Solution: Create finish_fixture(fixture, home_score, away_score, db) that atomically: settles the result → updates watchability → recalculates streaks. All 10 scattered call-sites become 1 function call. Delete update_fixture_score() as a standalone function — it becomes internal to the lifecycle module.

Candidate 3: Unify the API-Football Client

Strong 3 definitions, 2 callers use the wrong one, STATUS_MAP ignored

Problem: call_football_api() is defined in 3 places:

  1. seeder.py:72 — the canonical version, with provider="api_football" rate limiting
  2. providers/api_football.py:28 — identical but without the provider= rate limit param
  3. providers/api_football.py:63 — ApiFootballProvider.call_api() delegates to #2

The rate-limiting discrepancy means that the new IngestionEngine (which uses the provider) bypasses the rate limiter while the legacy seeder doesn't. This is a subtle quota-eating bug.

Meanwhile, providers/api_football.py defines STATUS_MAP (line 10-25) — the one canonical status mapping — but nobody imports it. Instead, 5 call sites inline their own if status_short in ("FT", "AET", "PEN") chains with slight variations (some include "LIVE", some don't).

Solution: Delete from seeder.py. Make providers/api_football.py:call_football_api() the single definition with the rate-limit provider= param. Export STATUS_MAP and parse_status(short) → str. Replace all inline status chains.

Candidate 4: Split tournament.py's 3 concerns

Worth exploring tournament.py — 970 lines, 12 functions, 3 concerns

Problem: tournament.py contains 3 distinct concerns mixed into one file:

  • Knockout Propagation (write-path): propagate_knockout_fixtures() + NEXT_ROUND_LOOKUP + resolve_placeholder_name() — mutates fixtures, creates new ones
  • Fixture Enrichment (read-path): enrich_fixture() + group_enriched_fixtures() — formats data for the API/UI, used by feed_builder.py
  • Query Orchestration: get_grouped_fixtures(), get_recommended_fixtures(), get_country_details(), get_group_details(), get_calendar_fixtures(), get_fixture_details_by_id(), get_all_third_placed_teams(), evaluate_nations_league_promotions()

Key friction: enrich_fixture() is the most-imported function — called by 5 query functions internally AND by feed_builder.py externally. But modifying enrichment logic risks breaking knockout propagation because they share the same file. simulation_results.json is read inline at 2 separate points in this file (lines 693 and 760).

Solution: Split into 3 modules: knockout.py, enrichment.py, queries.py. Enrichment becomes reusable by both queries and feed_builder.

Candidate 5: Deepen the Watchability Scoring module

Worth exploring scoring.py — 492 lines, 6 inline DB queries

Problem: calculate_watchability() is a 300-line procedural function that takes (fixture, home_team, away_team, db, weights), performs 6 inline DB queries (goal stats ×4, standings, TournamentTeam), reads simulation_results.json, and builds narrative text. The wrapper update_fixture_score() exists only to call it and write the result back — a pass-through with no logic.

Hidden import cycle: scoring.py does a deferred from backend.services.standings import calculate_standings inside the function body (line 216) to avoid a circular import. This means the dependency exists but is invisible to static analysis tools.

Solution: Narrow to score(fixture, db) → WatchabilityResult. Absorb all DB lookups, weight resolution, regional baselines, and the update_fixture_score wrapper. But this has lower leverage than Candidates 1-3 because it has fewer callers and the duplication it causes is already captured by Candidate 2 (the settle+score pairing).

Candidate 6: Kill the format_adapters.py god class

Critical format_adapters.py — 653 lines, CompetitionSyncAdapter is 525 lines

Problem: CompetitionSyncAdapter is a 525-line god class containing:

  • sync_results(): 260 lines of fixture sync, fallback API resolution, team matching, ELO sync, ClubELO sync with inline name-map file reads — this one method does more than most modules
  • sync_live_scores(): 250 lines with 3 nested fallback branches, each copy-pasting the same fixture-matching loop. Contains the is_mocked production mock detection (65 lines of test hooks in prod code)
  • ELO sync logic (international + club) embedded inside sync_results() (lines 344-380) — this belongs in elo.py

The "adapter" pattern is a lie: BaseFormatAdapter has two subclass slots, but CompetitionSyncAdapter is the only implementation. get_format_adapter() always returns it. The strategy pattern has collapsed to a single class.

Solution: Move ELO sync into elo.py. Move fixture-matching loop into a shared helper. Delete mock-detection code; use dependency injection or test-specific adapters. The remaining sync logic can live in updater.py directly — the adapter indirection adds no value when there's only one adapter.

Candidate 7: Centralize simulation_results.json reads

Spec-level 5 independent file reads across 3 modules

Problem: simulation_results.json is read at 5 separate call sites across 3 modules, each constructing the file path independently and opening the file with its own try/except. Some guard with tournament_id == 1 (hardcoded WC check), others don't.

  • tournament.py:693 — get_all_third_placed_teams(), guarded by tournament_id == 1
  • tournament.py:760 — get_group_details(), guarded by tournament_id == 1
  • scoring.py:12 — get_simulation_probabilities(), no tournament guard
  • simulation.py:157 — write path
  • simulation.py:656 — another write path

Solution: Create simulation.get_probabilities(tournament_id) → dict with internal caching. All 5 reads become 1 function call. The tournament_id == 1 guard should be a parameter, not hardcoded.

Frontend Architecture Review

8 JS files (270 KB), 1 CSS file (120 KB), 6 HTML pages — zero shared modules

Every page-specific JS file re-declares the same functions, the same data structures, and the same event handlers from scratch. There is no module system, no shared utility file, no build step. Candidate 8: Extract shared.js — kill 42 duplicated definitions

Critical ~1,440 lines of copy-paste across 6 JS files → 1 shared module

Problem: The frontend has no shared module. Every page (app.js, group.js, recommended.js, bracket.js, calendar.js, team.js) independently defines the same utilities. Total duplicated function definitions: 42 (6×COUNTRY_FLAGS, 6×getFlagUrl, 5×resolveAndTimezoneFetch, 15×getRating* trio, 6×showToast, 4×openMatchDetails). This is the worst architectural defect in the entire codebase by raw duplication count.

Active bug from divergence: getFlagUrl() in app.js handles apiId fields and falls back to api-sports.io for club badges. The version in recommended.js, bracket.js, calendar.js, and team.js does not — club badges silently 404 to default.png on those pages. This is a live visual regression caused by copy-paste drift.

Performance bug: Every page navigation fires a fresh fetch('https://ipapi.co/json/') call because the timezone resolution result is never cached in a shared location. A user clicking Home → Groups → Calendar → Bracket makes 4 separate geo-IP API calls when 1 would suffice.

Solution: Create frontend/js/shared.js (~180 lines). Move all shared logic there. Load it via <script src="/js/shared.js"> before the page-specific scripts. Each page script shrinks by ~200-300 lines and gets the canonical implementation for free.
